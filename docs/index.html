The core idea

What if accessibility was a constraint during code generation, not a fix applied afterward?

AI coding tools like Cursor, Lovable, Base44, and Claude Code can generate full interfaces from a prompt. But without explicit guidance, they produce code with basic accessibility failures — missing labels, broken keyboard support, invented ARIA patterns.

This project is a single, copyable prompt that transforms an AI coding assistant into a cautious accessibility engineer. It enforces bounded, traceable fixes on the most impactful accessibility issues — the ones that affect real users the most.

The goal is not compliance. The goal is reducing accessibility risk at the moment code is written.

Why this matters now: As AI generates more of the web, accessibility failures will scale with it. Fixing this at the source — during generation — is more effective than fixing it downstream. This is accessibility as infrastructure, not as afterthought.

Without guardrails, AI gets accessibility wrong

Observed failure modes when asking AI tools to "fix accessibility":

  • ×

    Compliance hallucinations

    Models claim "WCAG compliant" with no basis, creating legal risk in enterprise contexts.

  • ×

    Invented ARIA patterns

    Models fabricate ARIA roles and attributes that don't exist in any specification.

  • ×

    Runaway refactors

    What starts as an accessibility fix becomes a full UI redesign, breaking working code.

  • ×

    Design system damage

    Models aggressively change brand colors for contrast, ignoring intentional design decisions.

  • ×

    Scope creep

    Fixes for a login form cascade into typography changes, icon swaps, and global updates.

  • ×

    Overconfident output

    No distinction between verified fixes and best-effort guesses. Everything looks certain.

How the enforcement loop works

A controlled remediation protocol, not an autonomous refactor engine.

  1. 1

    Select enforcement mode

    Choose Basic-Safety, Public-Facing, or Enterprise-Critical. The AI will not proceed without a declared mode — this prevents it from guessing your risk context.

  2. 2

    Identify critical flows

    The AI identifies 1–3 critical user flows (login, checkout, onboarding). Fixes are scoped only to components in those flows.

  3. 3

    Evaluate 9 risk categories

    Keyboard operability, focus management, labeling, semantics, forms, structure, reflow, contrast, and complex components — prioritized by real-world impact.

  4. 4

    Apply bounded fixes

    Maximum 4 files per run. No global refactors. The AI stops after each batch and asks if you want to continue. Staged commits, not autonomous rewrites.

  5. 5

    Produce traceable output

    Issues list with WCAG Success Criteria references, a summary of fixes applied, and a prioritized backlog of remaining risks. Audit-style documentation, not vague suggestions.

Three enforcement modes

The right level of enforcement depends on your context. The AI won't proceed without an explicit choice.

Basic-Safety

Internal tools

Minimal exposure. Fixes keyboard traps, missing labels, and critical semantic gaps. For admin dashboards, internal apps, and low-risk interfaces.

Public-Facing

Public websites

Moderate exposure. Adds focus management, structure, and reflow checks. For marketing sites, SaaS products, and anything with broad user reach.

Enterprise-Critical

Regulated products

Full enforcement. WCAG citations, defensibility language, complex component patterns. For products under procurement scrutiny or VPAT requirements.

An unexpected discovery

During testing, after running the enforcement prompt, we asked the AI to build an unrelated component: "Create a city filter dropdown." Accessibility was never mentioned.

Yet the generated component included ARIA combobox attributes, keyboard navigation, accessible labeling, and semantic structure.

The enforcement prompt appears to function as session-level education. Once activated, accessibility becomes a default constraint for the rest of the AI session — even for unrelated tasks.

If this effect proves consistent, enforcement prompts could serve as both remediation (fix existing code) and preventive guidance (influence how AI generates new code).

What this experiment is not

  • A guarantee of WCAG compliance
  • A replacement for accessibility testing
  • A replacement for accessibility expertise
  • An automated accessibility overlay
  • A fix for every accessibility issue
